# Тестовая стратегия СМП

---

## 1. Назначение документа

Стратегия описывает долгосрочный подход к тестированию СМП: зачем мы тестируем систему именно так, как распределены усилия между сервисами и уровнями, и что осознанно оставлено вне области тестирования. Стратегия не привязана к конкретному спринту — она задаёт рамку, внутри которой составляется [тестовый план](test-plan.md) и проектируются тест-кейсы.

## 2. Объект тестирования

СМП — микросервисный симулятор процессингового центра. Полный путь транзакции:

```text
Terminal / Merchant Simulator → Gateway → Switch → Authorization → Card Management → ответ
                                             ↓
                                RabbitMQ → Transaction Logger → PostgreSQL → Web Dashboard
```

| Компонент | Порт | Роль в цепочке |
|---|:---:|---|
| Gateway | 8080 | Единая точка входа, валидация REST-контракта |
| Card Management | 8081 | Данные карт, лимиты, баланс, резервирование |
| Switch | 8082 | Маршрутизация по BIN, публикация в RabbitMQ |
| Authorization | 8083 | Решение APPROVED/DECLINED — вся бизнес-логика |
| Merchant Simulator | 8084 | Генератор мерчант-трафика |
| Terminal Simulator | 8085 | Генератор POS-трафика |
| Transaction Logger | 8088 | Запись транзакций, поиск, WebSocket |
| Bin Lookup | 8096 | Внешнее обогащение issuerId по BIN |
| Notification Service | 8097 | Асинхронные уведомления о карточных событиях |
| Web Dashboard | 3000 | Визуализация |
| PostgreSQL / RabbitMQ | 5432 / 5672 | Хранилище и брокер |

Система **уже реализована**. Мы не разрабатываем её, а проверяем поведение относительно технических заданий в [`tz/`](../../tz/) и контракта [`docs/api-spec.md`](../api-spec.md).

## 3. Цель тестирования

Цель — получить обоснованное суждение о том, принимает ли СМП **корректное платёжное решение** по каждой транзакции и **корректно ли отражает последствия этого решения** в состоянии карты и в журнале транзакций. Всё остальное — производные цели.

Такая формулировка задаёт приоритет: дефект, из-за которого одобряется транзакция сверх лимита или дважды списываются средства, критичнее дефекта вёрстки дашборда, даже если второй заметнее. Поэтому усилия распределяются не равномерно по сервисам, а пропорционально цене ошибки.

Стратегия — **риск-ориентированная**: глубина проверок определяется произведением «вероятность отказа × ущерб от отказа». Практическое следствие — деление системы на ядро и периферию (раздел 4) и разная техника тест-дизайна для них (раздел 6).

## 4. Приоритизация: ядро и периферия

### 4.1. Реестр рисков

| ID | Риск | Вероятность | Ущерб | Приоритет | Чем покрываем |
|---|---|:---:|:---:|:---:|---|
| R-01 | Транзакция одобрена сверх дневного/месячного лимита | Средняя | Критический | **P1** | Границы лимитов, pairwise, интеграционные тесты `limit_usage` |
| R-02 | Транзакция одобрена при недостаточном балансе | Средняя | Критический | **P1** | Границы баланса, E2E-сценарий покупки |
| R-03 | Одобрена операция по неактивной/заблокированной/просроченной карте | Средняя | Критический | **P1** | Классы эквивалентности статусов, pairwise |
| R-04 | Средства зарезервированы, но ответ DECLINED (или наоборот) — рассогласование баланса и решения | Средняя | Критический | **P1** | Интеграционные тесты Authorization ↔ CMS, проверка баланса после отказа |
| R-05 | Гонка при параллельной авторизации: «проверить баланс → зарезервировать» не атомарна (прямо отмечено в [`tz/04`](../../tz/04-authorization.md)) | Высокая | Высокий | **P1** | Нагрузочный smoke, конкурентные интеграционные тесты |
| R-06 | Дублирование RRN — перезапись транзакции в Logger и некорректный поиск | Средняя | Высокий | **P2** | Проверка уникальности RRN под нагрузкой |
| R-07 | Неверный порядок проверок: клиент получает не ту причину отказа | Высокая | Средний | **P2** | Тест-кейсы на приоритет проверок (TC-AUTH-24) |
| R-08 | Потеря транзакции при недоступности RabbitMQ / Logger | Средняя | Высокий | **P2** | Интеграционные тесты очереди, DLQ, reversal |
| R-09 | Сгенерирован PAN, не проходящий проверку Луна, или коллизия PAN | Низкая | Высокий | **P2** | Проверка генератора, алгоритм Луна |
| R-10 | Расхождение реализации и контракта `api-spec.md` (коды ответов, значения по умолчанию) | Высокая | Средний | **P2** | Контрактные API-тесты, сверка кодов ответов с `api-spec.md` |
| R-11 | Деградация внешнего Bin Lookup ломает авторизацию вместо graceful degradation | Средняя | Средний | **P3** | Негативные интеграционные тесты с недоступным bin-lookup |
| R-12 | Дашборд показывает неактуальные данные | Низкая | Низкий | **P3** | Чек-лист критического пути |

### 4.2. Деление системы

**Ядро — Authorization и Card Management.** В этих двух сервисах сосредоточены риски R-01…R-05 и R-09: именно здесь принимается решение и изменяется состояние карты. Для ядра строится полная модель тест-дизайна — классы эквивалентности, граничные значения и попарное тестирование ([test-design.md](test-design.md)).

**Периферия — Gateway, Switch, симуляторы, Transaction Logger, Bin Lookup, Notification Service, Web Dashboard.** Их поведение — это маршрутизация, трансляция и отображение: пространство состояний узкое, а цена ошибки ниже. Для периферии достаточно классов верхнего уровня и чек-листов ([checklists.md](checklists.md)). Глубокая модель здесь не даёт соразмерного эффекта — это осознанное решение, а не экономия.

## 5. Уровни тестирования

| Уровень | Что проверяет | Обоснование | Практика курса |
|---|---|---|:---:|
| **Unit** | Ветвления бизнес-логики: статусы, границы лимитов и баланса, Луна, генерация RRN/authCode | Самый дешёвый способ покрыть комбинаторику ядра; ветвления доступны без запуска инфраструктуры | 3 |
| **API / компонентный** | REST-контракты каждого сервиса: коды ответов, валидация, decline-коды | Контракт — граница между командами; расхождения (R-10) ловятся только здесь | 4 |
| **Интеграционный** | Authorization ↔ CMS, Switch ↔ RabbitMQ ↔ Logger, БД в контейнерах | Риски R-04, R-05, R-08 живут в стыках и невидимы для unit-тестов | 4 |
| **E2E** | Сквозные бизнес-сценарии: покупка, возврат, отказ | Подтверждает, что цепочка из 6 сервисов даёт корректный итог | 5 |
| **Нагрузочный smoke** | p50/p95/p99, throughput, error rate на 500+ транзакциях | Единственный способ проявить гонки (R-05) и коллизии RRN (R-06) | 6 |

Распределение усилий следует пирамиде: основная масса проверок — на unit- и API-уровне, E2E — только для ключевых бизнес-сценариев. Тест-дизайн, спроектированный в практике 2, переиспользуется на всех уровнях: один и тот же класс эквивалентности проверяется unit-тестом в Authorization и подтверждается E2E-сценарием.

## 6. Подход к тест-дизайну

| Техника | Где применяется | Почему |
|---|---|---|
| Классы эквивалентности | Ядро: статусы карт, суммы относительно лимитов и баланса, форматы PAN/expiryDate/BIN | Сокращает перебор без потери покрытия поведения |
| Граничные значения (ON/OFF) | Ядро: `dailyLimit`, `monthlyLimit`, `availableBalance`, `expiryDate`, длины полей, пагинация | Сравнения `≤`/`<` — типовой источник ошибок на единицу |
| Попарное тестирование (PICT) | Ядро: комбинация статуса, срока, трёх сумм, типа терминала, MCC, доступности CMS | 8 параметров дают 7776 комбинаций; попарный набор из 29 строк покрывает все достижимые пары |
| Чек-листы | Периферия, дымовое тестирование, критический путь | Даёт быстрый обзор работоспособности без проектирования данных |

Правила, принятые в проекте:

1. Позитивные и негативные классы выделяются раздельно; **в одном негативном кейсе — ровно одно невалидное значение**, иначе причину отказа невозможно локализовать.
2. Для каждой границы берутся три точки: ниже границы, ровно на границе (ON) и за границей (OFF).
3. Модель попарного тестирования обязательно содержит ограничения: без них генератор выдаёт недостижимые комбинации (например, «карта BLOCKED и превышен лимит» — до проверки лимита алгоритм не доходит).
4. Покрытие всех пар не считается доказательством полноты: критичные тройки, известные из реестра рисков, добавляются в набор вручную.

**Вне области тест-дизайна практики 2 сознательно оставлены** таблицы решений и диаграммы переходов состояний — они разбираются в следующем модуле курса. Модель статусов карты (`ACTIVE → BLOCKED → …`) здесь покрывается классами эквивалентности, а не графом переходов.

## 7. Область тестирования

### 7.1. В области

- Бизнес-логика авторизации: статусы, срок действия, лимиты, баланс, резервирование (ядро).
- CRUD карт, генерация тестовых карт, алгоритм Луна, пагинация и фильтрация (ядро).
- REST-контракты всех сервисов в части кодов ответов и валидации входа.
- Сквозной путь транзакции и её запись в журнал.
- Поведение при недоступности зависимостей: Card Management, Bin Lookup, RabbitMQ.
- Базовая производительность на smoke-уровне (500+ транзакций локально).

### 7.2. Вне области — и почему

| Что исключено | Основание |
|---|---|
| Безопасность (PCI DSS, шифрование PAN, маскирование) | Тестовая среда; ТЗ прямо разрешает возвращать незамаскированный PAN. Реальных данных держателей карт в системе нет |
| Антифрод-мониторинг, клиринг, взаиморасчёты | Отсутствуют в системе по проектному решению ([`docs/archive/program-overview.md`](../archive/program-overview.md), раздел «Упрощения») |
| Соответствие ISO 8583 на уровне битовых полей | Формат эмулируется упрощённым JSON; проверяется соответствие JSON-контракту, а не стандарту |
| Кросс-браузерное и мобильное тестирование Web Dashboard | Дашборд — вспомогательный инструмент визуализации, риск R-12 низкий |
| Локализация, доступность (a11y), UX | Не входят в цели учебного симулятора |
| Отказоустойчивость инфраструктуры (падение PostgreSQL, сетевые разделения) | Требует инфраструктурного стенда, недоступного в рамках курса; частично покрыто проверкой graceful degradation на уровне сервисов |
| Нагрузочное тестирование в CI | Раннеры GitHub Actions (2 ядра, 7 ГБ) не дают воспроизводимых метрик; в CI остаётся только smoke-прогон скрипта |

## 8. Тестовые данные и окружения

- **Окружение**: локальный `docker compose up -d` — 11 сервисов, PostgreSQL, RabbitMQ; тот же состав в CI.
- **Данные**: только синтетические карты из генератора CMS (`POST /api/cards/generate`). Продакшн-данные не используются и не существуют.
- **Изоляция**: каждый набор тестов сам создаёт нужные карты через API и не полагается на состояние, оставленное другими наборами. Карты с редкими статусами (`BLOCKED`, `EXPIRED`) готовятся через `PATCH /api/cards/{pan}` — генератор выдаёт их с вероятностью 2–3 % и полагаться на случайность нельзя.
- **Учёт лимитов**: таблица `limit_usage` накапливает суммы за день; тесты на границы лимитов либо используют свежую карту, либо явно приводят накопленную сумму к нужному значению.

## 10. Метрики и критерии качества

| Метрика | Целевое значение | Зачем |
|---|:---:|---|
| Покрытие требований ядра тест-кейсами | 100 % требований `tz/04`, `tz/05` | Ни одно требование не остаётся без проверки |
| Покрытие ветвлений бизнес-логики ядра (unit) | ≥ 80 % | Ветвления — носители рисков R-01…R-03 |
| Покрытие decline-кодов | 100 % кодов из `api-spec.md` | Каждый код отказа воспроизводим |
| Доля достижимых пар в попарном наборе | 100 % | Проверяется при генерации набора |
| Открытые дефекты Critical/High на момент сдачи | 0 | Критерий выхода (см. [test-plan.md](test-plan.md)) |
| Доля нестабильных (flaky) тестов | < 2 % | Нестабильный набор не даёт судить о качестве |

## 11. Роли и ответственность

Курс выполняется индивидуально, поэтому все роли совмещены; разделение приведено, чтобы зафиксировать зоны ответственности.

| Роль | Ответственность |
|---|---|
| Тест-аналитик | Анализ ТЗ, классы, границы, модель PICT, трассировка |
| Тест-инженер | Реализация unit/API/интеграционных и E2E-тестов, поддержка стабильности набора |
| DevOps-инженер | CI-пайплайн, quality gates, окружение из docker compose |
| Владелец качества (преподаватель) | Приёмка артефактов, проверка по рубрике |

## 12. Сопровождение стратегии

Стратегия пересматривается при изменении ТЗ ядра, при появлении нового сервиса в цепочке транзакции и по итогам каждого прогона с дефектами Critical/High: если дефект не был предсказан реестром рисков раздела 4, реестр дополняется, а глубина проверок соответствующей области повышается.
