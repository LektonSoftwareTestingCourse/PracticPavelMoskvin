# Чек-листы СМП: smoke-тестирование и критический путь

---

## 1. Назначение

Чек-лист — упорядоченный перечень **что** проверяется, без конкретных входных данных, шагов и ожидаемых результатов. В отличие от тест-кейсов ([test-design.md](test-design.md)), чек-лист не описывает данные: он служит быстрым обзором работоспособности.

Согласно [стратегии](test-strategy.md#42-деление-системы) периферийные сервисы — Gateway, Switch, симуляторы, Transaction Logger, Bin Lookup, Notification Service, Web Dashboard — покрываются чек-листами и классами верхнего уровня, а не полной моделью тест-дизайна: пространство их состояний узкое, а цена ошибки ниже. Ядро (Authorization, Card Management) присутствует здесь только на уровне дымовых проверок — его глубокая модель находится в [test-design.md](test-design.md).

Ниже три перечня:

| Раздел | Когда применяется | Длительность |
|---|---|---|
| [2. Дымовое тестирование](#2-чек-лист-дымового-тестирования) | После каждой сборки / развёртывания — перед любыми другими проверками | ~5 минут |
| [3. Критический путь](#3-чек-лист-критического-пути) | Перед сдачей артефакта и после изменений в цепочке транзакции | ~20 минут |
| [4. Периферийные сервисы](#4-чек-листы-периферийных-сервисов) | При изменениях в конкретном сервисе | по сервису |

Отметка `[x]` ставится только при фактически выполненной проверке.

## 2. Чек-лист дымового тестирования

Цель — за минимальное время ответить на вопрос «система вообще работоспособна?». Невыполнение любого пункта означает **критерий приостановки** по [test-plan.md, раздел 5.1](test-plan.md#51-приостановка): дальнейшие проверки бессмысленны. Автоматизированный эквивалент — [`scripts/smoke-test.sh`](../../scripts/smoke-test.sh) / [`smoke-test.ps1`](../../scripts/smoke-test.ps1).

### 2.1. Инфраструктура

- [ ] `docker compose up -d` завершается без ошибок
- [ ] `docker compose ps` — все контейнеры в состоянии `Up (healthy)`, ни один не перезапускается циклически
- [ ] PostgreSQL принимает подключения, миграции применены при старте
- [ ] RabbitMQ Management UI доступен на `http://localhost:15672`
- [ ] В логах сервисов при старте нет `ERROR` и исключений

### 2.2. Доступность сервисов

- [ ] Gateway — `GET :8080/health` → 200, перечислены состояния зависимых сервисов
- [ ] Card Management — `GET :8081/health` → 200, есть поле `cardsInDatabase`
- [ ] Switch — `GET :8082/health` → 200
- [ ] Authorization — `GET :8083/health` → 200, зависимость `cardManagement` в состоянии `ok`
- [ ] Merchant Simulator — `GET :8084/health` → 200
- [ ] Terminal Simulator — `GET :8085/health` → 200
- [ ] Transaction Logger — `GET :8088/health` → 200
- [ ] Bin Lookup — `GET :8096/actuator/health` → 200
- [ ] Notification Service — `GET :8097/actuator/health` → 200
- [ ] Web Dashboard — `http://localhost:3000` отдаёт страницу

### 2.3. Базовая функциональность

- [ ] Генерация тестовых карт `POST /api/cards/generate` создаёт не менее 20 карт
- [ ] Список карт `GET /api/cards` возвращает непустую выдачу и корректное `total`
- [ ] Обогащение по BIN `GET :8096/api/bin/400000` возвращает эмитента
- [ ] Одна транзакция `POST /api/transactions` по активной карте возвращает `APPROVED` и `responseCode = 00`
- [ ] В ответе присутствуют непустые `rrn` (12 цифр) и `authCode` (6 символов)
- [ ] Транзакция найдена в журнале: `GET /api/transactions/search?limit=5`
- [ ] Статистика `GET /api/dashboard/stats` отражает выполненную транзакцию
- [ ] Симулятор терминалов `POST /api/simulator/terminal/run` отправляет пакет транзакций без ошибок
- [ ] `./scripts/smoke-test.sh` завершается сообщением `ALL CHECKS PASSED`

## 3. Чек-лист критического пути

Критический путь — ключевые пользовательские сценарии процессинговой цепочки. Проверяется не только итоговый ответ, но и согласованность состояния всех участников цепочки.

### 3.1. Успешная покупка (happy path)

- [ ] Транзакция по активной карте в пределах лимитов и баланса завершается `APPROVED`
- [ ] Цепочка пройдена целиком: Gateway → Switch → Authorization → Card Management
- [ ] `issuerId` определён Switch по BIN и передан дальше
- [ ] Средства списаны с `availableBalance` ровно один раз и ровно на сумму транзакции
- [ ] Использованный лимит увеличен в `limit_usage` за текущий день и месяц
- [ ] Транзакция записана в журнал с корректными `rrn`, `authCode`, `responseCode`, суммой и `merchantId`
- [ ] Транзакция появилась в дашборде и в потоке WebSocket
- [ ] `processingTimeMs` в ответе заполнен и правдоподобен

### 3.2. Отказы по бизнес-правилам

- [ ] Неактивная карта (`INACTIVE`) → `DECLINED`, причина `CARD_INACTIVE`
- [ ] Заблокированная карта (`BLOCKED`) → `DECLINED`, причина `CARD_BLOCKED`
- [ ] Просроченная карта (статус `EXPIRED` или истёкший `expiryDate`) → `DECLINED`, `responseCode = 54`
- [ ] Несуществующая карта → `DECLINED`, `responseCode = 14`
- [ ] Превышен дневной лимит → `DECLINED`, `responseCode = 61`
- [ ] Превышен месячный лимит → `DECLINED`, `responseCode = 61`
- [ ] Недостаточно средств → `DECLINED`, `responseCode = 51`
- [ ] При любом отказе баланс карты **не изменился**, а `limit_usage` **не вырос**
- [ ] Каждая отклонённая транзакция записана в журнал с причиной отказа
- [ ] Поиск по `declineReason` в журнале находит отклонённые транзакции

### 3.3. Возврат и откат

- [ ] Reversal (`mti = 0400`) по существующему `rrn` возвращает сумму на баланс
- [ ] После reversal запись в `limit_usage` уменьшена на сумму операции
- [ ] Повторный reversal по тому же `rrn` не выполняет второй возврат
- [ ] Reversal по несуществующему `rrn` отклоняется с внятной причиной

### 3.4. Деградация зависимостей

- [ ] Card Management остановлен → авторизация отвечает отказом, а не таймаутом и не 500
- [ ] Bin Lookup остановлен → авторизация продолжает работать (graceful degradation), ответ укладывается в таймауты 3 с / 5 с
- [ ] RabbitMQ остановлен → синхронный путь транзакции сохраняет работоспособность, сообщения не теряются молча
- [ ] Transaction Logger недоступен → Switch выполняет откат авторизации, средства не остаются зарезервированными
- [ ] После восстановления зависимости система возвращается в рабочее состояние без перезапуска

### 3.5. Массовый поток

- [ ] Симулятор терминалов: 50 транзакций проходят, счётчики `approved + declined` сходятся с `totalSubmitted`
- [ ] Симулятор мерчантов: транзакции проходят по всем заявленным MCC
- [ ] Все RRN в пакете уникальны
- [ ] Число записей в журнале совпадает с числом отправленных транзакций — потерь нет
- [ ] Ошибок 5xx в ответах нет

## 4. Чек-листы периферийных сервисов

### 4.1. Gateway (8080)

- [ ] Все обязательные эндпоинты из [`api-spec.md`](../api-spec.md) отвечают
- [ ] Запрос с отсутствующим обязательным полем → 400, а не 500
- [ ] Запрос с полем неверной длины (`pan`, `stan`, `mcc`, `currencyCode`) → 400
- [ ] Недоступность внутреннего сервиса транслируется как 503, а не как 200 с пустым телом
- [ ] Ответ соответствует контракту: присутствуют `mti`, `stan`, `responseCode`, `status`
- [ ] Неизвестный маршрут → 404

### 4.2. Switch (8082)

- [ ] Известный BIN маршрутизируется к соответствующему `issuerId`
- [ ] Неизвестный BIN обрабатывается предсказуемо (отказ с внятным кодом, не 500)
- [ ] `issuerId` проставлен в запросе, уходящем в Authorization
- [ ] Транзакция публикуется в RabbitMQ для Logger и Notification Service
- [ ] При недоступности Logger выполняется откат авторизации

### 4.3. Transaction Logger (8088)

- [ ] Транзакция сохраняется в БД со всеми полями запроса и ответа
- [ ] Поиск работает по каждому фильтру: `pan`, `status`, `dateFrom`/`dateTo`, `merchantId`, `declineReason`
- [ ] Пагинация: `limit` и `offset` дают непересекающиеся страницы, `total` не зависит от страницы
- [ ] Статистика `/stats` согласована с содержимым журнала (`approved + declined = total`)
- [ ] `/recent` возвращает транзакции в порядке убывания времени
- [ ] WebSocket `/ws/transactions` передаёт новые транзакции в реальном времени
- [ ] Повторная запись транзакции с тем же RRN не создаёт дубль

### 4.4. Bin Lookup (8096)

- [ ] Существующий BIN → `issuerId`, `bankName`, `countryCode`
- [ ] Несуществующий BIN → 404, а не 500
- [ ] BIN неверной длины → 400
- [ ] Время ответа укладывается в таймауты потребителя (3 с connect, 5 с read)

### 4.5. Notification Service (8097)

- [ ] События о создании, изменении и удалении карты поступают в очередь `card-notifications`
- [ ] Формат сообщения соответствует контракту карточного события
- [ ] При недоступности RabbitMQ события не теряются: outbox удерживает их со статусом `PENDING` и повторяет публикацию
- [ ] После трёх неудачных попыток событие помечается `FAILED` и остаётся видимым для разбора

### 4.6. Terminal / Merchant Simulator (8085 / 8084)

- [ ] Каждый заявленный сценарий терминала (`normal`, `mixed`, `high_value`, `night_time`, `declines_test`) запускается
- [ ] Каждый сценарий мерчанта (`grocery`, `electronics`, `restaurant`, `travel`) запускается
- [ ] Симулятор использует карты из пула CMS, а не выдуманные PAN
- [ ] Итоговые счётчики в ответе сходятся: `approved + declined = totalSubmitted`
- [ ] `elapsedMs` заполнен и правдоподобен
- [ ] Сценарий `declines_test` действительно порождает отказы

### 4.7. Web Dashboard (3000)

- [ ] Страница загружается без ошибок в консоли браузера
- [ ] Отображается список последних транзакций
- [ ] Агрегированная статистика соответствует данным `GET /api/dashboard/stats`
- [ ] Новая транзакция появляется в списке без перезагрузки страницы (WebSocket)
- [ ] При недоступном backend интерфейс показывает состояние ошибки, а не пустой экран
