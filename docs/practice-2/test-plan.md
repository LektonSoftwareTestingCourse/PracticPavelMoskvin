# Тестовый план СМП

Стратегия отвечает на вопрос «почему тестируем так»; план отвечает на вопросы **что, как, кем, когда и при каких условиях** проверки начинаются, приостанавливаются и считаются завершёнными.

---

## 1. Область тестирования и подход

### 1.1. Что тестируется

| Область | Объекты | Уровни | Приоритет |
|---|---|---|:---:|
| Ядро: решение по транзакции | Authorization (`POST /api/internal/authorize`), алгоритм проверок 1–7, `limit_usage`, генерация RRN/authCode | unit, API, интеграционный, E2E | P1 |
| Ядро: данные карт | Card Management (CRUD, `generate`, `reserve`, Луна, пагинация) | unit, API, интеграционный | P1 |
| Вход в систему | Gateway: валидация REST-контракта, проброс ошибок | API | P2 |
| Маршрутизация | Switch: выбор эмитента по BIN, публикация в RabbitMQ, откат при недоступности Logger | API, интеграционный | P2 |
| Журнал транзакций | Transaction Logger: запись, поиск, пагинация, статистика, WebSocket | API, интеграционный | P2 |
| Внешние зависимости | Bin Lookup (timeout, retry, graceful degradation), Notification Service (outbox → RabbitMQ) | интеграционный | P3 |
| Источники трафика | Terminal / Merchant Simulator | чек-лист, E2E | P3 |
| Визуализация | Web Dashboard | чек-лист | P3 |
| Производительность | Сквозной путь транзакции под нагрузкой 500+ | нагрузочный smoke | P2 |

### 1.2. Что не тестируется

Перечень исключений и оснований зафиксирован в [test-strategy.md, раздел 7.2](test-strategy.md#72-вне-области--и-почему): безопасность и PCI DSS, антифрод и клиринг, соответствие ISO 8583 на уровне битовых полей, кросс-браузерность и UX дашборда, локализация и доступность, отказоустойчивость инфраструктуры, нагрузочные метрики в CI.

### 1.3. Подход

1. Требования ядра из [`tz/04-authorization.md`](../../tz/04-authorization.md) и [`tz/05-card-management.md`](../../tz/05-card-management.md) нумеруются (`REQ-AUTH-xx`, `REQ-CMS-xx`) — см. [test-design.md, раздел 2](test-design.md#2-требования).
2. К каждому требованию применяются техники тест-дизайна: классы эквивалентности → граничные значения → попарный набор.
3. Тест-кейсы проектируются один раз и реализуются на том уровне пирамиды, где проверка дешевле всего; E2E-уровень получает только сквозные бизнес-сценарии.
4. Периферия покрывается чек-листами дымового тестирования и критического пути.
5. Каждый прогон завершается сверкой с критериями выхода (раздел 4).

## 2. Тестовые окружения

| Окружение | Состав | Назначение | Кто разворачивает |
|---|---|---|---|
| Локальное | `docker compose up -d`: 11 сервисов + PostgreSQL + RabbitMQ | Разработка тестов, отладка, нагрузочный прогон 500+ | Тест-инженер |
| Локальное изолированное | Testcontainers (PostgreSQL) + поднятый сервис | Интеграционные тесты с БД | Автоматически из тестов |
| CI лёгкое | GitHub Actions, без docker-образов сервисов | Линтеры, компиляция, unit-тесты — на каждый push | GitHub Actions (`ci.yml`) |
| CI тяжёлое | GitHub Actions + docker compose | Smoke, E2E, load-smoke — вручную перед сдачей | GitHub Actions (`practice-run.yml`) |

Требования к локальному окружению: Docker Desktop, свободные порты 3000, 5432, 5672, 8080–8097, 15672; не менее 8 ГБ RAM.

## 3. Критерии входа

Тестирование очередной области начинается, когда выполнено всё перечисленное:

| # | Критерий входа | Как проверяется |
|:---:|---|---|
| 1 | ТЗ проверяемого сервиса прочитано, требования пронумерованы | Раздел 2 [test-design.md](test-design.md#2-требования) |
| 2 | `docker compose up -d` поднимает все контейнеры в состоянии `Up (healthy)` | `docker compose ps` |
| 3 | `./scripts/smoke-test.sh` завершается `ALL CHECKS PASSED` | Вывод скрипта |
| 4 | Сгенерирован пул тестовых карт (≥ 20 через `POST /api/cards/generate`) | Ответ API, `cardsInDatabase` в `/health` CMS |
| 5 | Спроектированы тест-кейсы на проверяемое требование | [test-design.md](test-design.md) |
| 6 | Лёгкий CI-пайплайн зелёный на текущей ветке | GitHub Actions |

Невыполненный критерий 2 или 3 означает, что дефект лежит в окружении, а не в логике: результаты такого прогона недостоверны и не учитываются.

## 4. Критерии выхода

Тестирование области считается завершённым при одновременном выполнении:

| # | Критерий выхода | Измеримое значение |
|:---:|---|---|
| 1 | Требования ядра покрыты тест-кейсами | 100 % `REQ-AUTH-*` и `REQ-CMS-*` присутствуют в матрице трассировки |
| 2 | Спроектированные тест-кейсы выполнены | 100 % кейсов имеют статус Passed или Failed (ни одного Not Run) |
| 3 | Доля успешных тест-кейсов | ≥ 95 % Passed |
| 4 | Открытые дефекты Critical | 0 |
| 5 | Открытые дефекты High | 0 (либо принятое владельцем качества обоснование отсрочки) |
| 6 | Открытые дефекты Medium/Low | Зафиксированы в бэклоге с приоритетом; не блокируют сдачу |
| 7 | Покрытие ветвлений бизнес-логики ядра unit-тестами | ≥ 80 % |
| 8 | Все decline-коды из `api-spec.md` воспроизведены хотя бы одним кейсом | 100 % |
| 9 | Попарный набор покрывает все достижимые пары | 100 % достижимых пар покрыто |
| 10 | Нестабильные тесты | < 2 % от общего числа, каждый — с объяснением причины |
| 11 | Артефакты прогона оформлены | Отчёт + баг-репорты в `docs/practice-N/` |

## 5. Критерии приостановки и возобновления

### 5.1. Приостановка

Прогон останавливается, если наступило любое из событий:

| # | Событие приостановки | Почему продолжать бессмысленно |
|:---:|---|---|
| 1 | Один или несколько контейнеров не поднимаются либо не проходят health-check | Отказы будут массовыми и не связанными с логикой |
| 2 | Card Management недоступен | Все транзакции отклоняются с `SERVICE_UNAVAILABLE` — проверяется инфраструктура, а не бизнес-правила |
| 3 | Блокирующий дефект в ядре: неверное решение по транзакции воспроизводится на большинстве кейсов | Дальнейшие результаты не добавляют информации |
| 4 | Более 30 % тест-кейсов падают по одной и той же причине | Признак общего дефекта или испорченного окружения |
| 5 | Тестовые данные повреждены (например, `limit_usage` содержит суммы от предыдущих прогонов) | Результаты по границам лимитов недостоверны |
| 6 | Изменилось ТЗ ядра в ходе прогона | Ожидаемые результаты устарели |

### 5.2. Возобновление

| # | Условие возобновления |
|:---:|---|
| 1 | Причина приостановки устранена и зафиксирована в отчёте |
| 2 | Окружение перезапущено с чистым состоянием (`docker compose down -v && docker compose up -d`) |
| 3 | Дымовой чек-лист ([checklists.md, раздел 2](checklists.md#2-чек-лист-дымового-тестирования)) пройден полностью |
| 4 | Тест-кейсы, упавшие до приостановки, перезапущены целиком, а не выборочно |
| 5 | При изменении ТЗ — затронутые кейсы и ожидаемые результаты актуализированы |

## 8. Риски плана и меры

| ID | Риск выполнения плана | Влияние | Мера |
|---|---|:---:|---|
| PR-01 | Нестабильность окружения (порты, нехватка памяти, долгий старт контейнеров) съедает время | Высокое | Проверка критериев входа перед каждым прогоном; `down -v` между прогонами |
| PR-02 | Накопленное состояние `limit_usage` и балансов искажает проверки границ | Высокое | Свежая карта на каждый кейс границ; явная подготовка состояния через API |
| PR-03 | Генератор карт выдаёт `BLOCKED`/`INACTIVE` с вероятностью 2–3 % — нужных данных может не оказаться | Среднее | Явная подготовка статусов через `PATCH /api/cards/{pan}` |
| PR-04 | Расхождения ТЗ и реализации превращаются в спор «дефект или уточнение требования» | Среднее | Расхождения выявляются на этапе тест-дизайна и выносятся владельцу требований до прогона |
| PR-05 | Гонки и коллизии RRN не воспроизводятся на малых объёмах | Среднее | Отдельный конкурентный сценарий и нагрузочный прогон 500+ |
| PR-06 | Тяжёлый CI расходует квоту Actions-минут | Низкое | Запуск только перед сдачей, как предусмотрено регламентом |
| PR-07 | Совмещение ролей одним исполнителем — нет независимого взгляда | Среднее | Взаимное рецензирование артефакта, самопроверка по чек-листу |

## 9. Метрики и отчётность

Собираются по каждому прогону:

- количество спроектированных / выполненных / успешных тест-кейсов;
- покрытие требований (матрица трассировки [test-design.md, раздел 7](test-design.md#7-матрица-трассировки));
- покрытие ветвлений бизнес-логики ядра (JaCoCo);
- распределение дефектов по severity и по сервисам;
- для нагрузочного прогона — p50/p95/p99, throughput, error rate, среднее время ответа.

Отчётность: результаты каждой практики публикуются в `docs/practice-N/`, ссылка на зелёный прогон CI прикладывается к Issue со сдачей.
